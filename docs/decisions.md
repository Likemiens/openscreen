# Product and architecture decisions

Этот журнал фиксирует решения персональной кастомизации, чтобы они не исчезали внутри кода и
следующих prompt-сессий.

## D-001 — `main` остаётся зеркалом upstream

Решение: не коммитить персональные функции в `main`. Релизная персональная версия живёт в
долгоживущей ветке `creator-edition`; новые изменения начинаются в коротких feature-ветках от `creator-edition`.

Причина: `main` можно обновлять через `git merge --ff-only upstream/main`, а различия и конфликты
видны отдельно.

## D-002 — Интеграции изолируются от recorder pipeline

Решение: облачные провайдеры реализуются в `electron/integrations/` и вызываются после создания
`RecordingSession`. Нативные Windows/macOS helper contracts не меняются.

Причина: native capture — самая хрупкая и активно меняющаяся часть upstream. Изоляция снижает
стоимость каждого обновления.

## D-003 — Локальная запись является source of truth до подтверждения облака

Решение: Stop всегда создаёт локальный draft и не делает сетевых запросов. При включённой очистке
export и source bundle удаляются только после проверки типа и размера удалённого файла и только
после выхода из текущего редактора. Ошибка export, upload или проверки сохраняет локальную запись.

## D-004 — Проверяемая пользовательская папка Яндекс Диска

Решение: использовать `cloud_api:disk.read` и `cloud_api:disk.write` для пути
`disk:/OpenScreen Exports`. Перед сохранением настроек и каждым upload приложение проверяет, что
папка соответствует публичной ссылке `https://disk.yandex.ru/d/GKhvA2QkXOBe2g`.

Причина: публичная папка находится вне изолированного `app:/`, а чтение метаданных необходимо для
проверки назначения и размера загруженного файла.

## D-005 — Токен хранится только в main process

Решение: renderer передаёт токен один раз через IPC; main process шифрует его Electron
`safeStorage`. Обратно возвращается только `connected: boolean`.

Запрещено: `localStorage`, `.env` в репозитории, открытые JSON-конфиги, логирование token/body.

## D-006 — Manual token перед полным OAuth

Решение: для личного pilot используется OAuth debug token. Authorization Code + PKCE добавляется
только если интеграция становится продуктовой или используется несколькими людьми.

Причина: это самый дешёвый RAT ценности; client registration и redirect UX пока не являются
критическим путём.

## D-007 — Публикуется итоговый MP4, а не raw screen track

Решение: Publish сначала запускает штатный editor export, затем main process загружает полученный
MP4. Это правило одинаково для фоновой публикации сразу после Stop и для Publish из редактора.

Причина: raw screen track не содержит webcam composition, cursor overlay и правки. Пользователь
ожидает получить на Диске готовый к просмотру ролик.

## D-008 — Персональный HUD фиксирован на английском и horizontal layout

Решение: убрать language picker, system-language prompt, Notes и vertical tray. Английский становится
default locale, webcam получает живой preview, а cursor mode описывает текущее состояние и
последствия для редактора.

Причина: это персональная сборка для одного workflow; невостребованные controls создают шум и
ухудшают понимание основного сценария.

## D-009 — HUD не попадает в запись, а Stop открывает export launcher

Дата: 2026-08-02.

Решение: Electron HUD использует content protection, поэтому остаётся поверх экрана для управления,
но исключается из screen capture. Во время записи HUD показывает timer, Stop, Restart и Delete.
После Stop локальный draft открывается в компактной карточке с названием, Quality, FPS и действиями
Save Anywhere, Edit in Studio и Publish & Get Link.

Publish создаёт публичную ссылку на конкретный файл Яндекс Диска и копирует её в clipboard только
после проверки upload. Save Anywhere и Publish используют один и тот же editor export pipeline.

Причина: управление записью должно всегда оставаться доступным, но не загрязнять видео; настройки
экспорта должны выбираться один раз до фоновой операции.

## D-010 — Recording Recipes хранятся локально и не меняют native recorder

Дата: 2026-08-03.

Решение: HUD содержит три встроенных recipe — Product Demo, Quick Update и Tutorial — и позволяет
сохранить текущую конфигурацию как custom recipe. Recipe восстанавливает mic/camera device,
system audio, cursor mode, countdown, Quality/FPS и сохранённый source. Screen/window переиспользуется
только после повторного поиска среди доступных sources; исчезнувшее окно не подменяется другим.

Recipe state хранится в versioned `localStorage`, не содержит OAuth-секретов и не передаётся в main
process. Export settings копируются в локальный recording draft в момент завершения записи. Native
Windows/macOS capture contracts не меняются.

Причина: повторная настройка HUD находится до каждого take на Critical Chain, а renderer-only модель
даёт основную экономию времени с минимальной стоимостью upstream sync.

## D-011 — Quick clip: запись сохраняется сразу после Stop

Дата: 2026-10-07.

Контекст: главный сценарий — записать короткий фрагмент интерфейса, сохранить и отправить. Раньше
любое сохранение запускало скрытый редактор и полный render, даже когда править было нечего.

Решение: запись с системным курсором и без камеры считается quick clip. Сразу после Stop она
превращается в итоговый MP4 в папке пользователя (по умолчанию `Videos\OpenScreen`): если кроп и
масштаб не нужны — файл копируется без перекодирования, иначе выполняется один проход
decode → crop/scale → encode через WebCodecs (`mediabunny` Conversion) прямо в окне HUD. Сырой
захват после этого удаляется. Редактируемый курсор или камера оставляют прежний путь через Studio
(D-007, D-009). Если быстрый путь не сработал, запись остаётся и открывается панель draft.

Альтернативы: кроп и масштаб в нативном helper (нужен C++-тулчейн и своя сборка под каждую
платформу); новый захват через WebCodecs в renderer (мгновенно, но это второй recorder со своими
рисками синхронизации звука).

Последствия: D-003 сохраняется — сеть после Stop не трогается. Для quick clip «локальная копия» —
это файл в папке пользователя, поэтому публикация такого клипа никогда его не удаляет
(`keepLocal`), а настройка удаления после загрузки относится только к экспорту из Studio.

Условие пересмотра: появление нативного кропа/масштаба в helper'ах.

## D-012 — Запись области = запись дисплея + кроп

Дата: 2026-10-07.

Решение: область выбирается в прозрачном оверлее на весь дисплей и хранится в DIP относительно
дисплея. Записывается весь дисплей нативным recorder'ом, а кроп применяется при сохранении клипа
через доли кадра, поэтому не зависит от масштаба и разрешения захвата. Контуры native helper не
меняются (D-002). Area-клипы всегда идут быстрым путём: курсор в кадре, камера недоступна.

Причина: нативный helper не умеет кроп, а пересобрать его без тулчейна нельзя. Кроп на этапе
сохранения даёт тот же результат ценой одного быстрого прохода.

## D-013 — Приложение живёт в трее, HUD выгружается в простое

Дата: 2026-10-07.

Решение: на Windows и macOS закрытие HUD прячет его в трей, а не завершает приложение. Скрытый HUD
через 60 секунд уничтожается (остаются main-процесс, трей и хоткей) и создаётся заново по хоткею
или из трея; настройка записи для этого хранится в `localStorage`, а не в состоянии React.
Опция Launch at login запускает приложение сразу в трей (`--hidden`). На Linux закрытие последнего
окна по-прежнему завершает приложение: трей там ненадёжен.

Причина: мгновенный старт записи требует живого процесса, а «занимать меньше» — отсутствия
лишнего renderer'а, пока он не нужен.

## D-014 — Глобальный хоткей записи с запасными вариантами

Дата: 2026-10-07.

Решение: один хоткей начинает захват и останавливает идущую запись. По умолчанию пробуются по
очереди Win+Shift+R, Ctrl+Alt+R, Win+Shift+X, Ctrl+Shift+Space — регистрируется первый свободный;
пользователь может задать свой в настройках HUD. Хранится отдельно от шорткатов редактора, в
`app-settings.json`.

Причина: Win+Shift+R в Windows 11 занят записью экрана «Ножниц», и регистрация такого сочетания
молча не срабатывает. Запасной список даёт рабочий хоткей без настройки.

## D-015 — Графитовый HUD в духе macOS

Дата: 2026-10-07.

Решение: HUD перестроен как плавающая графитовая панель: сегмент Area / Window / Screen,
переключатели звука и камеры, чип формата, красная Record; редкие настройки под `⋯`. Заменяет
wine-tinted surface из D-008/D-009; английский интерфейс и отсутствие Notes, language picker и
vertical tray остаются в силе. Recording Recipes (D-010) сохранены как Recording presets в меню
`⋯`; при запуске восстанавливается последняя использованная конфигурация, а не выбранный recipe.

Причина: строка должна читаться за секунду и вести к одному действию — записать.

## D-016 — Мокапы устройств: геометрия и настоящие пропорции экрана

Дата: 2026-10-07 (пересмотрено в тот же день).

Решение: рамка устройства — чистая геометрия в `src/lib/deviceFrame.ts`: список скруглённых
прямоугольников и кругов в долях короткой стороны экрана. Preview (`layoutVideoContent`) и экспорт
(`FrameRenderer`) получают её через общий `computeFramedCompositeLayout` и рисуют одними и теми же
Pixi `Graphics` — слой под видео и слой поверх (вырез камеры).

У телефона (9:19.5), планшета (11" iPad, 1640:2360) и ноутбука (16:10) экран фиксированных
пропорций. Устройство не растягивается под видео: его можно только масштабировать целиком (Scale)
и повернуть (Portrait / Landscape у телефона и планшета). Видео кладётся на экран в режиме **Fill**
(покрывает экран, лишнее обрезает маска; по умолчанию) или **Fit** (целиком, с чёрными полями).
Окно браузера стандартного размера не имеет, поэтому только оно повторяет форму видео.

Первая версия подгоняла рамку под пропорции видео (телефон «ложился» под горизонтальную запись и
менял форму при обрезке). Отклонено пользователем: устройство должно выглядеть как настоящее и
иметь стандартный размер.

Альтернатива — PNG/SVG-ассеты конкретных моделей — отклонена: утяжеляет сборку, несёт чужой
дизайн, а preview и экспорт пришлось бы сводить отдельно.

Последствия: рамка есть в `EditorState` (undo/redo), в файле проекта (`normalizeDeviceFrame`,
поля `orientation` и `fit` со значениями по умолчанию для старых проектов) и блокирует быстрый
путь «копия исходника» при экспорте. В full-bleed раскладках камеры (vertical-stack, dual-frame)
рамка не рисуется. При выбранном устройстве скругление задаёт экран устройства, слайдер Corners
скрыт. Курсор проецируется на нарисованное видео (`croppedRect`), а не на маску: в режиме Fill
картинка больше маски.

## D-017 — Studio в графитовой палитре, вкладка Frame — первая

Дата: 2026-10-07.

Решение: редактор переведён с «зелёное на чёрном» на палитру HUD (D-015): нейтральные графитовые
поверхности и один синий акцент `#0A84FF`. Инспектор открывается на новой вкладке **Frame**
(видео-источник, устройство, aspect ratio, Scale, Corners, пиксельный Crop, Background); её
контролы — `src/components/video-editor/studioControls.tsx` (секция с линией, сегмент,
слайдер-строка, select, числовое поле, toggle). Вкладки Effects и Timeline собраны из них же;
отдельной вкладки Background больше нет — фон стал последней секцией Frame.
Roundness и Padding ушли из Effects в Frame (Corners и Scale), чтобы не было двух регуляторов
одного значения. Цвета, попадающие в сам ролик (аннотации по умолчанию), не менялись.

Причина: выбранное в инспекторе — это светлая заливка, а не цвет, поэтому единственным цветным
объектом на экране остаётся редактируемое видео.

## D-018 — Обрезка в пикселях исходника поверх нормализованного crop

Дата: 2026-10-07.

Решение: поля Top / Bottom / Left / Right в Frame задают отступы в пикселях исходного видео
(`src/lib/cropInsets.ts`); в состоянии редактора по-прежнему хранится нормализованный
`cropRegion`, пересчёт идёт через целые пиксели в обе стороны. Минимум остатка — 16 px по оси.

Причина: «срезать 5 px сверху» должно давать ровно 5 и читаться обратно как 5; визуальный
редактор обрезки остаётся для подбора на глаз и показывает те же числа.

## D-019 — Один Pixi `Application` нельзя уничтожать с `destroy(true)`

Дата: 2026-10-07.

Контекст: в редакторе одновременно живут два Pixi-приложения — preview и рендерер экспорта.
`app.destroy(true, …)` в Pixi 8.18 дополнительно вызывает `GlobalResourceRegistry.release()`,
который уничтожает batch-объекты, ещё используемые вторым приложением. После экспорта следующий
кадр preview падал с `Cannot read properties of null (reading 'geometry')`, и его ticker больше
не запускался (превью пустело до перезапуска редактора).

Решение: все Pixi-приложения уничтожаются через `destroyPixiApp` (`src/lib/pixiDestroy.ts`) —
`destroy({ removeView: true }, …)` без освобождения глобальных пулов.

## D-020 — Таймлайн: видео — одна дорожка-клип, которую режут на куски

Дата: 2026-10-07.

Контекст: обрезка делалась строкой Trim, куда клавишей T добавлялся красный блок фиксированной
ширины. По отзыву пользователя это неочевидно: не видно, что блок — вырезанная часть самого видео.

Решение: первая строка таймлайна — клип (`timeline/ClipTrack.tsx`): полоса с кадрами видео
(`useFilmstripFrames`), поделённая на куски. **Split** (T) ставит разрез в позиции плейхеда,
клик выбирает кусок, **Remove** (Delete) вырезает его. Вырезанный кусок остаётся на дорожке
заштрихованным блоком, его края можно тянуть, **Restore** возвращает. Референс — редактор Loom:
шкала времени исходника не схлопывается, поэтому зумы, аннотации и скорость в нижних строках
остаются на своих местах.

Модель: вырезанный кусок — это прежний `TrimRegion` (воспроизведение, экспорт и субтитры уже их
пропускают), ничего нового в рендерере не понадобилось. Новое в состоянии — только
`clipSplits: number[]` (где поделено оставшееся видео; undo/redo, сохраняется в проекте). Куски
вычисляются функцией `computeClipPieces` из длительности, разрезов и trim-регионов.

Цвета элементов таймлайна — системная палитра: zoom синий, full camera фиолетовый, speed
оранжевый, annotation жёлтый; плейхед белый.

## D-021 — Экспорт из одной кнопки в заголовке

Дата: 2026-10-07.

Контекст: видео уходило из Studio тремя путями — Save Local и Publish в заголовке и Export Video
на отдельной вкладке инспектора, где прятались формат и качество, которые использовал и Save
Local. Publish без подключённого Яндекс Диска отвечал тостом «вернитесь в рекордер».

Решение: одна кнопка **Export** справа в заголовке (`ExportMenu.tsx`). В меню сначала «что» —
формат (MP4 / GIF) и качество, затем «куда» — **Save to computer…** или **Publish & copy link**.
Если Яндекс Диск не подключён, вместо Publish стоит **Connect Yandex Disk to publish…**: панель
подключения открывается прямо в Studio, и после подключения публикация продолжается. Для GIF
Publish отключён с объяснением (ссылки публикуются только как MP4). Вкладка Export и подвал
инспектора убраны; из ссылок поддержки осталась звезда — на репозиторий форка
(`src/lib/appLinks.ts`).

Test id прежние (`testId-export-panel-button`, `testId-mp4-format-button`,
`testId-gif-format-button`, `testId-export-button`), поэтому upstream-спека экспорта работает без
изменений.

## D-022 — Headless-запуск не трогает машину пользователя

Дата: 2026-10-07.

Решение: при `HEADLESS=true` вместе с собственным профилем (`--user-data-dir`) приложение не
создаёт иконку в трее, не регистрирует глобальные хоткеи и не берёт общий lock единственного
экземпляра. Тесты и проверки можно запускать, пока пользователь работает и пока открыт
установленный OpenScreen. Оба условия обязательны: случайная переменная `HEADLESS` в окружении не
оставит обычный запуск без трея.

Причина: установленное приложение держит lock, и тестовый экземпляр молча завершался; без lock он
занимал следующий свободный хоткей записи и добавлял вторую иконку в трей.

## Как добавлять решения

Для каждого нового решения указывать дату, контекст, выбранный вариант, альтернативы, причину,
последствия и условие пересмотра.
